\section{前言}

本次实验中，我将在已实现的基于NTT算法的多项式乘法代码的基础上，尝试进行GPU并行化实现。

GPU（图形处理单元）具有大量的并行计算核心，非常适合于数据并行的计算任务。NTT算法中的蝶形操作具有良好的并行性，使其成为GPU加速的理想候选。

实验中，我将首先分析NTT算法的并行化方案，设计合适的GPU线程划分策略；随后实现基于CUDA的NTT算法，包括基础版本和优化版本；最后通过性能测试对比CPU和GPU版本的效果，分析加速比和优化效果。

\paragraph{实验环境} 本次实验在配备NVIDIA GeForce RTX 4060 Laptop GPU的系统上进行，使用CUDA 12.5进行开发，编译器为nvcc。

\paragraph{实验设计} 本实验基于64位数据类型实现，测试数据使用项目提供的标准测试样例。

\section{基本原理}

\subsection{GPU并行计算模型}

GPU采用SIMT（Single Instruction, Multiple Threads）并行计算模型，通过大量的轻量级线程来执行相同的指令操作不同的数据。GPU的硬件架构包含多个流式多处理器（SM），每个SM包含多个CUDA核心。

在CUDA编程模型中，线程被组织为网格（Grid）和线程块（Block）的层次结构。线程块内的线程可以通过共享内存进行通信和同步，而不同线程块之间的线程无法直接同步。

\subsection{CPU与GPU并行策略的根本差异}

要理解本次GPU编程实验的核心思路，必须首先认识CPU多线程编程与GPU编程在并行粒度选择上的根本差异。在Lab3多线程实验中，我们分析了NTT算法的并行化策略，但GPU编程需要完全不同的思路。

\begin{algorithm}[htbp]
\caption{NTT算法的三层循环结构（来自Lab3分析）}
\label{alg:ntt_structure}
\begin{algorithmic}[1]
\Require 多项式系数数组 $a$, 长度 $n$, 模数 $p$, 原根 $\omega$
\Ensure 变换后的频域系数 $a$
\For{$mid = 1, 2, 4, \ldots, n/2$} \Comment{外层循环：必须串行}
    \State $W_n \gets \omega^{(p-1)/(2 \cdot mid)}$
    \For{$j = 0, 2 \cdot mid, 4 \cdot mid, \ldots, n - 2 \cdot mid$} \Comment{中层循环：可并行}
        \State $w \gets 1$
        \For{$k = 0, 1, 2, \ldots, mid - 1$} \Comment{内层循环：有循环携带依赖}
            \State $x \gets a[j + k]$
            \State $y \gets w \cdot a[j + k + mid]$
            \State $a[j + k] \gets x + y$
            \State $a[j + k + mid] \gets x - y$
            \State $w \gets w \cdot W_n$ \Comment{关键依赖：w依赖于前一次迭代}
        \EndFor
    \EndFor
\EndFor
\end{algorithmic}
\end{algorithm}

\paragraph{CPU多线程的粗粒度并行特征} Lab3的分析表明，CPU多线程编程应该对\textbf{第二层j循环进行并行化}。具体而言，外层mid循环存在强数据依赖，必须串行执行；中层j循环中不同j块操作的数据区域完全独立，适合中等粒度并行化；内层k循环的旋转因子w具有循环携带依赖（$w_{k+1} = w_k \cdot W_n$），破坏依赖会导致算法错误。

这种策略的核心思想是：\textbf{CPU线程创建和调度开销较大，因此不宜将任务划分过细}。每个线程负责一个完整的j块计算（包含mid个蝶形操作），在线程内部串行执行k循环以保持数学正确性。

\paragraph{GPU编程的极细粒度并行需求} 与CPU多线程截然不同，GPU架构具有以下特征。\textbf{大规模并行计算单元}方面，现代GPU拥有数千个CUDA核心，需要大量线程才能充分利用硬件资源；\textbf{极低的线程调度开销}方面，GPU线程调度由硬件实现，单个线程的创建和切换成本极低；\textbf{SIMT执行模型}方面，线程以warp（32线程）为单位同步执行，最适合数据并行的细粒度操作。

因此，GPU编程的核心原则是：\textbf{应当将计算任务划分到最细的粒度，让每个线程处理最小的数据单元}。对于NTT算法，这意味着每个线程应该处理一个蝶形操作，而不是一个j块。

\subsection{GPU并行化的核心挑战：循环携带依赖的消除}

将CPU的粗粒度并行策略直接移植到GPU会严重浪费计算资源。真正的GPU并行化需要解决内层k循环的依赖问题，实现真正的极细粒度并行。

\paragraph{依赖问题分析} 在原始算法中，旋转因子w的计算存在严格的循环携带依赖：
$$w_0 = 1, \quad w_{k+1} = w_k \cdot W_n$$

这种依赖关系使得第k+1次蝶形操作必须等待第k次操作完成，无法并行执行。

\paragraph{依赖消除策略} GPU并行化的关键突破是认识到：每个蝶形操作所需的旋转因子可以独立计算。对于第k个蝶形操作，其旋转因子为：
$$w_k = W_n^k = \left(\omega^{(p-1)/(2 \cdot mid)}\right)^k$$

通过预计算所有可能的旋转因子并存储在GPU显存中，每个线程可以直接索引获取所需的w值，完全消除了循环携带依赖。

\subsection{极细粒度GPU并行化设计}

基于依赖消除策略，我们设计了真正的GPU并行化方案：

\paragraph{线程映射策略} 为每个蝶形操作分配一个GPU线程，实现完全的j、k循环并行化。\textbf{外层mid循环}保持在CPU主机端串行控制（数据依赖不可消除）；\textbf{中层j循环 + 内层k循环}完全扁平化为线程网格，每个线程处理一个蝶形操作；\textbf{旋转因子获取}通过预计算表直接索引，消除w的依赖关系。

\paragraph{线程索引计算} 每个GPU线程通过全局索引计算其负责的蝶形操作：

\begin{algorithm}[htbp]
\caption{GPU极细粒度并行化核心算法}
\label{alg:gpu_fine_grain}
\begin{algorithmic}[1]
\Require GPU数组 $a$, 预计算旋转因子表 $twiddles$, mid级别
\Ensure 完成所有蝶形操作的并行执行
\State $tid \gets blockIdx.x \times blockDim.x + threadIdx.x$
\If{$tid \geq n/2$} \textbf{return} \Comment{超出蝶形操作总数}
\EndIf
\State $step \gets 2 \times mid$
\State $j \gets (tid \div mid) \times step$ \Comment{确定j块位置}
\State $k \gets tid \bmod mid$ \Comment{确定块内k位置}
\State $tw\_idx \gets (mid - 1) + k$ \Comment{旋转因子表索引}
\State $w \gets twiddles[tw\_idx]$ \Comment{直接获取预计算的旋转因子}
\State $x \gets a[j + k]$
\State $y \gets w \times a[j + k + mid]$
\State $a[j + k] \gets x + y$
\State $a[j + k + mid] \gets x - y$
\end{algorithmic}
\end{algorithm}

这种设计实现了真正的极细粒度并行：对于长度为n的多项式，每个mid级别需要n/2个蝶形操作，我们启动n/2个线程并行执行，充分利用GPU的大规模并行计算能力。

\section{GPU编程策略分析}

上一节我们分析了GPU编程相比于CPU编程的不同点，重点关注了二者的硬件特征带来的\textbf{任务分配策略}的不同，同时为代码搭建实现提供了理论指导；而在本节，我们将分析GPU编程中不同\textbf{线程块配置}和\textbf{内存访问模式}带来的影响，为具体实现细节进行理论分析。

\subsection{线程块大小}

GPU性能很大程度上取决于合理的线程块大小和网格配置。基于RTX 4060的硬件特性（3072个CUDA核心，24个SM），我们分析了不同配置的性能影响。

\paragraph{线程块大小选择原理}
线程块大小必须考虑以下硬件约束：每个SM最多支持1024个线程；Warp大小为32，线程块大小应为32的倍数；共享内存限制（每个SM 48KB）；寄存器限制（每个SM 65536个32位寄存器）。

基于我们的核函数资源需求分析：每个线程需要约8个寄存器，无需共享内存，因此理论上每个SM可以支持满负荷的1024个线程。

\paragraph{线程块大小实验分析}
我们测试了不同线程块大小对性能的影响：

\subsection{内存访问模式}

\paragraph{合并内存访问设计}
我们的线程索引设计确保相邻线程访问相邻内存位置：

\begin{lstlisting}[language=C++]
int tid = blockIdx.x * blockDim.x + threadIdx.x;
int j = (tid / mid) * step;        // 确定j块位置
int k = tid % mid;                 // 确定块内k位置
// 相邻线程访问：a[j+k], a[j+k+1], a[j+k+2], ...
\end{lstlisting}

这种设计使得32个线程的Warp能够实现合并内存访问，将多个分散的内存访问合并为一个高带宽的传输。

\paragraph{旋转因子访问优化}
预计算的旋转因子表采用连续存储，线程通过简单的索引计算获取所需值：

\begin{lstlisting}[language=C++]
int tw_idx = (mid - 1) + k;        // 连续的索引访问
T w_mont = twiddles[tw_idx];       // 高效的内存访问
\end{lstlisting}

相比动态计算$W_n^k$，这种预计算策略避免了复杂的模幂运算，将计算密集型操作转换为内存访问优化问题。

\section{搭建实现}

\subsection{旋转因子预计算策略}

实现极细粒度GPU并行化的关键是消除旋转因子的循环携带依赖。我们通过预计算所有可能的旋转因子来解决这个问题。

\paragraph{旋转因子表生成} 对于每个mid级别，我们预计算该级别所需的所有旋转因子：

\begin{lstlisting}[language=C++]
template <typename T>
void generate_twiddle_table(std::vector<T> &table, T n, T p, T omega, bool inverse) {
    table.resize(n);
    MontMod<T> mont(p);
    T omega_mont = mont.from_T(omega);
    if (inverse) omega_mont = mont.inv(omega_mont);
    T one_mont = mont.from_T(1);

    for (int level = 0; (T(1) << level) < n; ++level) {
        T mid = T(1) << level;
        T exp = (p - 1) / (mid << 1);
        T Wn_mont = mont.pow(omega_mont, exp);
        T w = one_mont;
        T offset = mid - 1;
        for (T k = 0; k < mid; ++k) {
            table[offset + k] = w;
            w = mont.mul(w, Wn_mont);
        }
    }
}
\end{lstlisting}

通过这种预计算策略，每个线程可以通过简单的索引操作获取其所需的旋转因子，而无需进行复杂的模幂运算或依赖其他线程的计算结果。

\subsection{极细粒度并行核函数}

基于预计算的旋转因子表，我们实现了真正的极细粒度并行核函数：

\paragraph{核函数设计思路} 每个GPU线程负责处理一个蝶形操作，通过全局线程索引计算其在NTT算法中的位置，并直接索引获取所需的旋转因子。

\begin{lstlisting}[language=C++]
template <typename T, int MODE>
__global__ void ntt_stage_kernel_fwd_mode(T *a, const T *twiddles, int mid, int n, T p, T neg_r_inv, u64 mu) {
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    int total = n >> 1;
    if (tid >= total) return;

    int step = mid << 1;
    int j = (tid / mid) * step;        // 确定j块位置
    int k = tid % mid;                 // 确定块内k位置
    int tw_idx = (mid - 1) + k;        // 旋转因子表索引
    T w_mont = twiddles[tw_idx];       // 直接获取预计算的旋转因子

    T x = a[j + k];
    T y = mod_mul_unified<MODE>(w_mont, a[j + k + mid], p, neg_r_inv, mu);
    a[j + k] = gpu_mont_add_correct(x, y, p);
    a[j + k + mid] = gpu_mont_sub_correct(x, y, p);
}
\end{lstlisting}

这种实现的关键优势在于：每个线程完全独立，无需等待其他线程的计算结果；所有蝶形操作可以真正并行执行；充分利用GPU的大规模并行计算能力。

\paragraph{线程映射分析} 对于长度为n的多项式，每个mid级别需要n/2个蝶形操作。我们的线程映射策略如下：
\begin{algorithmic}[1]
\State $total\_butterflies \gets n/2$ \Comment{总蝶形操作数}
\State $BLOCK\_SIZE \gets 256$ \Comment{每个线程块包含256个线程}
\State $GRID\_SIZE \gets \lceil total\_butterflies / BLOCK\_SIZE \rceil$ \Comment{网格大小}
\State 启动 $GRID\_SIZE \times BLOCK\_SIZE$ 个线程并行执行
\end{algorithmic}

\subsection{多模乘算法支持}

为了深入分析GPU编程中不同算法的性能特征，我们实现了三种模乘算法的统一接口：

\begin{lstlisting}[language=C++]
template <int MODE, typename T>
__device__ inline T mod_mul_unified(T a, T b, T p, T neg_r_inv, u64 mu) {
    if constexpr (MODE == MUL_NAIVE) {
        return mod_mul_naive<T>(a, b, p);
    } else if constexpr (MODE == MUL_MONT) {
        return gpu_mont_mul_correct(a, b, p, neg_r_inv);
    } else { // MUL_BARRETT
        return mod_mul_barrett_32(a, b, p, mu);
    }
}
\end{lstlisting}

通过模板参数MODE在编译时选择具体的模乘算法，避免运行时的分支开销，同时便于性能对比分析。

\subsection{主机端控制逻辑}

主机端负责外层mid循环的串行控制，并为每个级别启动大规模并行的GPU计算：

\begin{lstlisting}[language=C++]
template <typename T, int MODE>
void poly_multiply_ntt_gpu_core(T *a, T *b, T *ab, T n, T p, T omega) {
    MontMod<T> montMod(p);
    T n_expanded = expand_n(2 * n - 1);
    
    // 预计算旋转因子表
    std::vector<T> tw_host(n_expanded);
    std::vector<T> tw_inv_host(n_expanded);
    generate_twiddle_table(tw_host, n_expanded, p, omega, false);
    generate_twiddle_table(tw_inv_host, n_expanded, p, omega, true);

    // 上传旋转因子表到GPU
    T *tw_gpu = nullptr;
    T *tw_inv_gpu = nullptr;
    CHECK_CUDA_CORRECT(cudaMalloc(&tw_gpu, n_expanded * sizeof(T)));
    CHECK_CUDA_CORRECT(cudaMalloc(&tw_inv_gpu, n_expanded * sizeof(T)));
    CHECK_CUDA_CORRECT(cudaMemcpy(tw_gpu, tw_host.data(), n_expanded * sizeof(T), cudaMemcpyHostToDevice));
    CHECK_CUDA_CORRECT(cudaMemcpy(tw_inv_gpu, tw_inv_host.data(), n_expanded * sizeof(T), cudaMemcpyHostToDevice));

    // NTT前向变换：真正的极细粒度并行
    const int BLOCK = 256;
    for (int level = 0; (T(1) << level) < n_expanded; ++level) {
        T mid = T(1) << level;
        int total_butterfly = n_expanded >> 1;      // 总蝶形操作数
        int GRID = (total_butterfly + BLOCK - 1) / BLOCK;  // 网格大小

        ntt_stage_kernel_fwd_mode<T, MODE><<<GRID, BLOCK>>>(a_mont_gpu, tw_gpu, mid, n_expanded, p, neg_r_inv, mu);
        ntt_stage_kernel_fwd_mode<T, MODE><<<GRID, BLOCK>>>(b_mont_gpu, tw_gpu, mid, n_expanded, p, neg_r_inv, mu);
        CHECK_CUDA_CORRECT(cudaGetLastError());
    }
    CHECK_CUDA_CORRECT(cudaDeviceSynchronize());
    
    // 点乘和逆变换...
}
\end{lstlisting}

这种实现的关键特点是：每次核函数启动都处理n/2个蝶形操作，充分利用GPU的并行计算能力，而不是像传统CPU思路那样逐个处理j块。

\subsection{GPU实现与CPU实现的区别}

\paragraph{并行粒度的根本改变} 从CPU的"每线程处理一个j块"转变为GPU的"每线程处理一个蝶形操作"，实现了从粗粒度到极细粒度的转变。

\paragraph{依赖关系的彻底消除} 通过预计算旋转因子表，将原本具有循环携带依赖的k循环完全并行化，突破了传统NTT实现的串行瓶颈。

\paragraph{内存访问的优化设计} 旋转因子通过连续的全局内存访问获取，减少了复杂的模幂运算，提升了GPU线程的计算效率。
