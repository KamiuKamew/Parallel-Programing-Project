\section{前言}

本次实验中，我将在已实现的基于NTT算法的多项式乘法代码的基础上，尝试进行GPU并行化实现。

GPU（图形处理单元）具有大量的并行计算核心，非常适合于数据并行的计算任务。NTT算法中的蝶形操作具有良好的并行性，使其成为GPU加速的理想候选。

实验中，我将首先分析NTT算法的并行化方案，设计合适的GPU线程划分策略；随后实现基于CUDA的NTT算法，包括基础版本和优化版本；最后通过性能测试对比CPU和GPU版本的效果，分析加速比和优化效果。

\paragraph{实验环境} 本次实验在配备NVIDIA GeForce RTX 4060 Laptop GPU的系统上进行，使用CUDA 12.5进行开发，编译器为nvcc。

\paragraph{实验设计} 本实验基于64位数据类型实现，测试数据使用项目提供的标准测试样例。

\section{基本原理}

\subsection{GPU并行计算模型}

GPU采用SIMT（Single Instruction, Multiple Threads）并行计算模型，通过大量的轻量级线程来执行相同的指令操作不同的数据。GPU的硬件架构包含多个流式多处理器（SM），每个SM包含多个CUDA核心。

在CUDA编程模型中，线程被组织为网格（Grid）和线程块（Block）的层次结构。线程块内的线程可以通过共享内存进行通信和同步，而不同线程块之间的线程无法直接同步。

\subsection{基于Lab3并行化分析的GPU设计}

在Lab3多线程编程实验中，我们已经深入分析了NTT算法的并行化位点。通过对三层嵌套循环的数据依赖性分析，我们确定了最佳的并行化策略：

\begin{algorithm}[htbp]
\caption{NTT算法的三层循环结构（来自Lab3分析）}
\label{alg:ntt_structure}
\begin{algorithmic}[1]
\Require 多项式系数数组 $a$, 长度 $n$, 模数 $p$, 原根 $\omega$
\Ensure 变换后的频域系数 $a$
\For{$mid = 1, 2, 4, \ldots, n/2$} \Comment{外层循环：必须串行}
    \State $W_n \gets \omega^{(p-1)/(2 \cdot mid)}$
    \For{$j = 0, 2 \cdot mid, 4 \cdot mid, \ldots, n - 2 \cdot mid$} \Comment{中层循环：可并行}
        \State $w \gets 1$
        \For{$k = 0, 1, 2, \ldots, mid - 1$} \Comment{内层循环：有循环携带依赖}
            \State $x \gets a[j + k]$
            \State $y \gets w \cdot a[j + k + mid]$
            \State $a[j + k] \gets x + y$
            \State $a[j + k + mid] \gets x - y$
            \State $w \gets w \cdot W_n$ \Comment{关键依赖：w依赖于前一次迭代}
        \EndFor
    \EndFor
\EndFor
\end{algorithmic}
\end{algorithm}

Lab3的关键发现是：\textbf{应该对第二层j循环进行并行化}，原因如下：
\begin{itemize}
\item \textbf{外层mid循环}：存在强数据依赖，当前层依赖前一层的完整结果，必须串行执行
\item \textbf{中层j循环}：不同j块操作的数据区域完全独立，天然适合并行化
\item \textbf{内层k循环}：旋转因子w具有循环携带依赖（$w_{k+1} = w_k \cdot W_n$），并行化会破坏算法正确性
\end{itemize}

\subsection{从多线程到GPU的设计演进}

基于Lab3的OpenMP实现经验，GPU版本的设计思路自然演进为：

\paragraph{OpenMP策略回顾} 在Lab3中，我们使用\texttt{\#pragma omp parallel for}对j循环进行并行化，每个线程负责一个j块的计算，块内的k循环保持串行以维护w的依赖关系。

\paragraph{GPU策略设计} 将OpenMP的成功策略映射到GPU架构：
\begin{itemize}
\item \textbf{网格级别}：外层mid循环在主机端串行控制，每次启动GPU核函数处理一个mid级别
\item \textbf{线程块级别}：每个线程块对应一个j块，负责处理长度为$2 \cdot mid$的数据
\item \textbf{线程级别}：每个线程块内只使用一个线程，串行执行k循环以保持w的依赖关系
\end{itemize}

这种设计虽然在单个线程块内没有充分利用并行性，但确保了算法的正确性，是GPU实现的稳健基础。

\section{搭建实现}

\subsection{GPU核函数设计}

基于Lab3确定的正确并行化策略，我们设计了GPU核函数。核心思想是严格对应CPU版本的算法结构，确保算法正确性。

\paragraph{Montgomery模运算设备函数}

首先实现GPU版本的Montgomery模运算，这是NTT算法的基础：

\begin{lstlisting}[language=C++]
template <typename T>
__device__ T gpu_mont_reduce(__uint128_t t, T mod, T neg_r_inv) {
    constexpr int word_bits = sizeof(T) * 8;
    T m = (T)t * neg_r_inv;
    __uint128_t tmp = t + (__uint128_t)m * mod;
    T res = (T)(tmp >> word_bits);
    res = res - (mod & -(res >= mod));
    return res;
}

template <typename T>
__device__ T gpu_mont_mul(T a_mont, T b_mont, T mod, T neg_r_inv) {
    return gpu_mont_reduce((__uint128_t)a_mont * b_mont, mod, neg_r_inv);
}
\end{lstlisting}

注意这里使用\texttt{\_\_uint128\_t}来处理64位乘法的128位中间结果，避免溢出问题。

\paragraph{NTT前向变换核函数}

基于Lab3的并行化策略，GPU核函数严格对应CPU版本的结构：

\begin{algorithm}[htbp]
\caption{GPU核函数设计（基于Lab3策略）}
\label{alg:gpu_kernel}
\begin{algorithmic}[1]
\Require GPU数组 $a_{mont}$, 当前mid级别, 模数参数
\Ensure 完成当前级别的蝶形操作
\State $mid \gets 2^{level}$
\State $j \gets blockIdx.x \times (2 \cdot mid)$ \Comment{每个线程块处理一个j块}
\If{$threadIdx.x \neq 0$} \textbf{return} \Comment{只使用第一个线程}
\EndIf
\State $W_n \gets \omega^{(p-1)/(2 \cdot mid)}$ \Comment{计算基础旋转因子}
\State $w \gets 1$ \Comment{初始化旋转因子}
\For{$k = 0, 1, \ldots, mid-1$} \Comment{串行执行k循环}
    \State $x \gets a_{mont}[j + k]$
    \State $y \gets w \times a_{mont}[j + k + mid]$
    \State $a_{mont}[j + k] \gets x + y$
    \State $a_{mont}[j + k + mid] \gets x - y$
    \State $w \gets w \times W_n$ \Comment{保持依赖关系}
\EndFor
\end{algorithmic}
\end{algorithm}

对应的CUDA实现为：

\begin{lstlisting}[language=C++]
template <typename T>
__global__ void ntt_forward_kernel(T *a_mont, T n, T p, T omega_mont, 
                                  T neg_r_inv, T one_mont, int mid_level) {
    T mid = T(1) << mid_level;
    T step = mid << 1;
    
    // 每个线程块处理一个j块
    T j = blockIdx.x * step;
    if (j >= n) return;
    
    // 只使用第一个线程（保证串行性）
    if (threadIdx.x != 0) return;
    
    // 计算Wn_mont（对应CPU版本）
    T exp = (p - 1) / (mid << 1);
    T Wn_mont = gpu_mont_pow(omega_mont, exp, p, neg_r_inv, one_mont);
    
    // 初始化w_mont为1（对应CPU版本）
    T w_mont = one_mont;
    
    // 串行执行k循环（保持w_mont依赖关系）
    for (T k = 0; k < mid; k++) {
        T x_mont = a_mont[j + k];
        T y_mont = gpu_mont_mul(w_mont, a_mont[j + k + mid], p, neg_r_inv);
        a_mont[j + k] = gpu_mont_add(x_mont, y_mont, p);
        a_mont[j + k + mid] = gpu_mont_sub(x_mont, y_mont, p);
        
        // 更新w_mont（对应CPU版本）
        w_mont = gpu_mont_mul(w_mont, Wn_mont, p, neg_r_inv);
    }
}
\end{lstlisting}

\subsection{主机端控制逻辑}

主机端严格对应CPU版本的外层mid循环控制：

\begin{lstlisting}[language=C++]
template <typename T>
void poly_multiply_ntt_gpu(T *a, T *b, T *ab, T n, T p, T omega) {
    MontMod<T> montMod(p);
    T n_expanded = expand_n(2 * n - 1);
    
    // 数据预处理（对应CPU版本）
    T *a_expanded = expand_a(a, n, n_expanded);
    T *b_expanded = expand_a(b, n, n_expanded);
    bit_reverse_permute(a_expanded, n_expanded);
    bit_reverse_permute(b_expanded, n_expanded);
    
    // 转换到Montgomery域并上传GPU
    T *a_mont_host = new T[n_expanded];
    T *b_mont_host = new T[n_expanded];
    for (T i = 0; i < n_expanded; i++) {
        a_mont_host[i] = montMod.from_T(a_expanded[i]);
        b_mont_host[i] = montMod.from_T(b_expanded[i]);
    }
    
    T *a_mont_gpu, *b_mont_gpu, *ab_mont_gpu;
    cudaMalloc(&a_mont_gpu, n_expanded * sizeof(T));
    cudaMalloc(&b_mont_gpu, n_expanded * sizeof(T));
    cudaMalloc(&ab_mont_gpu, n_expanded * sizeof(T));
    
    cudaMemcpy(a_mont_gpu, a_mont_host, n_expanded * sizeof(T), 
               cudaMemcpyHostToDevice);
    cudaMemcpy(b_mont_gpu, b_mont_host, n_expanded * sizeof(T), 
               cudaMemcpyHostToDevice);
    
    // NTT前向变换（对应CPU版本的外层循环）
    for (int level = 0; level < 32 && (T(1) << level) < n_expanded; level++) {
        T mid = T(1) << level;
        if (mid >= n_expanded) break;
        
        T num_j_blocks = n_expanded / (mid << 1);
        if (num_j_blocks > 0) {
            dim3 blockSize(1);  // 每个块只用一个线程
            dim3 gridSize(num_j_blocks);  // 线程块数 = j块数
            
            ntt_forward_kernel<<<gridSize, blockSize>>>(
                a_mont_gpu, n_expanded, p, omega_mont, neg_r_inv, one_mont, level);
            ntt_forward_kernel<<<gridSize, blockSize>>>(
                b_mont_gpu, n_expanded, p, omega_mont, neg_r_inv, one_mont, level);
            cudaDeviceSynchronize();
        }
    }
    
    // 点乘和逆变换...
}
\end{lstlisting}

\subsection{算法正确性保证}

该实现的关键优势在于严格保持了CPU版本的算法逻辑：

\begin{itemize}
\item \textbf{循环依赖保持}：通过在每个线程块内使用单线程串行执行k循环，完全保持了旋转因子w的循环携带依赖关系
\item \textbf{数据独立性}：不同线程块处理不同的j块，数据访问完全独立，避免了竞争条件
\item \textbf{算法一致性}：GPU版本的每一步都严格对应CPU版本，确保数学正确性
\end{itemize}

虽然这种实现在单个线程块内没有充分利用GPU的并行性（每个块只用一个线程），但它确保了算法的正确性，为后续优化提供了可靠的基础。

\paragraph{算法正确性分析}

从功能正确性角度，三种算法表现显著不同：

\begin{itemize}
\item \textbf{Montgomery模乘}：在所有测试用例中都输出正确结果（✅），证明了实现的可靠性
\item \textbf{Naive模乘}：在所有测试中都产生错误结果（❌），可能由于精度损失或溢出问题
\item \textbf{Barrett规约}：在64位测试中表现正确，但在32位测试中存在实现错误
\end{itemize}

\paragraph{性能特征分析}

从性能角度观察到以下重要规律：

\begin{enumerate}
\item \textbf{大规模问题优势明显}：在n=65536的大规模测试中，GPU版本比CPU快约2倍，验证了GPU在大规模并行计算中的优势。

\item \textbf{小规模问题启动开销}：小规模问题（n≤256）中GPU普遍较慢，这是由GPU固有的启动开销和内存传输成本造成的。

\item \textbf{Montgomery算法稳定性}：Montgomery模乘在各种规模下都表现出最佳的正确性和相对稳定的性能。

\item \textbf{算法复杂度影响}：虽然Barrett规约理论上更简单，但在GPU实现中并未显示出明显的性能优势，可能受限于GPU对复杂整数运算的支持。
\end{enumerate}

\section{拓展实验：进一步并行化尝试}

在完成了基于Lab3策略的GPU实现并验证其正确性后，我们尝试进一步优化GPU的并行度，以充分利用GPU的计算资源。

\subsection{更激进的并行化方案}

我们尝试了同时并行化第二层j循环和第三层k循环的方案：

\begin{algorithm}[htbp]
\caption{激进并行化方案（失败尝试）}
\label{alg:aggressive_parallel}
\begin{algorithmic}[1]
\State $j \gets blockIdx.x \times (2 \cdot mid)$ \Comment{线程块对应j块}
\State $k \gets threadIdx.x$ \Comment{线程对应k索引}
\If{$k < mid$}
    \State $w_{mont} \gets precomputed\_twiddles[k]$ \Comment{使用预计算旋转因子}
    \State 执行蝶形操作$(j+k, j+k+mid)$
\EndIf
\end{algorithmic}
\end{algorithm}

这种方案的设计思路是：
\begin{itemize}
\item 每个线程块处理一个j块（长度为$2 \cdot mid$）
\item 线程块内的每个线程并行处理不同的k值
\item 预计算所有旋转因子避免循环依赖
\end{itemize}

\subsection{失败原因分析}

经过实现和测试，这种激进并行化方案产生了错误的结果。深入分析发现失败的根本原因：

\paragraph{旋转因子依赖破坏} NTT算法中的旋转因子$w$具有严格的循环携带依赖关系：
$$w_{k+1} = w_k \cdot W_n, \quad w_0 = 1$$

这种依赖关系不仅仅是数值计算的便利，更是算法数学正确性的核心要求。任何试图打破这种依赖的并行化都会导致算法失效。

\paragraph{算法数学本质} NTT算法的每个循环级别内，旋转因子的递推关系保证了正确的频域变换。并行化k循环实质上是在试图改变NTT的数学定义，这在理论上是不可行的。
